remplacer la connexion

# Chemin du fichier SQLite (créé automatiquement à côté de app.py)
DATABASE = os.path.join(os.path.dirname(os.path.abspath(__file__)), 'database.db')

@app.teardown_appcontext
def close_connection(exception):
    db = getattr(g, '_database', None)
    if db is not None:
        db.close()

def get_db():
    db = getattr(g, '_database', None)
    if db is None:
        db = g._database = sqlite3.connect(DATABASE)
        db.row_factory = sqlite3.Row  # équivalent du DictCursor de pymysql
        db.execute("PRAGMA foreign_keys = ON")
    return db

adapter les CREATE TABLE

La syntaxe MySQL des CREATE TABLE ne passe pas telle quelle en SQLite :

MySQL SQLite
id int(11) NOT NULL AUTO_INCREMENT id INTEGER PRIMARY KEY AUTOINCREMENT
disponible tinyint(1) DEFAULT 0 disponible INTEGER DEFAULT 0
CONSTRAINT fk_xxx FOREIGN KEY (col) REFERENCES table(id) FOREIGN KEY (col) REFERENCES table(id)
varchar(50) varchar(50) — ne change pas (SQLite l’accepte tel quel)

Exemple avant/après :

-- MySQL
CREATE TABLE article (
  id int(11) NOT NULL AUTO_INCREMENT,
  nom varchar(50),
  disponible tinyint(1) DEFAULT 0,
  type_article_id int(11),
  PRIMARY KEY (id),
  CONSTRAINT fk_article_type_article FOREIGN KEY (type_article_id) REFERENCES type_article (id)
);
-- SQLite
CREATE TABLE article (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  nom varchar(50),
  disponible INTEGER DEFAULT 0,
  type_article_id INTEGER,
  FOREIGN KEY (type_article_id) REFERENCES type_article (id)
);

attention aux colonnes ambiguës (GROUP BY / ORDER BY)

Si une requête fait une jointure entre deux tables ayant une colonne du même nom (ex. id dans type_article et article), SQLite est plus strict que MySQL : un GROUP BY ou ORDER BY non qualifié provoque une erreur.

-- fonctionnait en MySQL, échoue en SQLite :
-- sqlite3.OperationalError: ambiguous column name: id
SELECT type_article.libelle, type_article.id, count(article.id) as nbr_articles
FROM type_article
LEFT JOIN article ON type_article.id = article.type_article_id
GROUP BY libelle, id
ORDER BY libelle;
-- correction : qualifier les colonnes
GROUP BY type_article.libelle, type_article.id
ORDER BY type_article.libelle;

ce qui NE change PAS

Pour rassurer les étudiants : une grande partie du code reste identique entre pymysql et sqlite3 : - les tuples de paramètres passés à .execute(sql, tuple_valeurs) - .fetchall() / .fetchone() / .commit() - l’accès row['colonne'] dans le code Python et les templates Jinja2 — grâce à db.row_factory = sqlite3.Row, chaque ligne se comporte comme un dictionnaire (accès par nom de colonne), exactement comme le faisait pymysql.cursors.DictCursor. Seul le mécanisme de connexion change, pas la façon de lire les résultats.
