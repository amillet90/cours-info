Fiche comparative : MySQL vs SQLite

Typage des données (déclaration dans un CREATE TABLE)

MySQL impose un typage strict : chaque type a une taille/précision vérifiée par le moteur (un VARCHAR(50) refuse une chaîne plus longue, un INT refuse une lettre).

SQLite fonctionne avec une affinité de type (type affinity) : il ne connaît que 5 classes de stockage en interne (NULL, INTEGER, REAL, TEXT, BLOB). Le nom de type qu’on écrit dans le CREATE TABLE (VARCHAR(50), INT, DECIMAL(10,2)…) sert juste à choisir l’affinité la plus proche — mais rien n’est vérifié : une colonne INTEGER peut très bien stocker du texte, une colonne VARCHAR(50) peut recevoir une chaîne de 500 caractères sans erreur.

Déclaration MySQL Équivalent / comportement SQLite
INT, INT(11), TINYINT, BIGINT affinité INTEGER — la taille ((11)) est ignorée
VARCHAR(50), CHAR(10), TEXT affinité TEXT — la longueur ((50)) est ignorée, jamais limitée
DECIMAL(10,2), NUMERIC affinité NUMERIC — la précision n’est pas garantie comme en MySQL
FLOAT, DOUBLE affinité REAL
BLOB affinité BLOB (aucune conversion)
TINYINT(1) (utilisé comme booléen) pas de type booléen : utiliser INTEGER avec des valeurs 0/1
ENUM('a','b','c') pas de type ENUM : utiliser TEXT + CHECK (colonne IN ('a','b','c')) si on veut contraindre les valeurs
UNSIGNED n’existe pas en SQLite (ignoré/erreur selon le contexte)
DATE, DATETIME, TIMESTAMP pas de type date natif : stocker en TEXT (format ISO8601) ou INTEGER/REAL (timestamp Unix ou jour julien), et utiliser les fonctions date(), datetime() pour manipuler

À retenir pour la pédagogie : en SQLite, les longueurs et précisions écrites dans un CREATE TABLE sont de la « documentation » pour qui relit le schéma, mais ne sont jamais imposées par le moteur.

Clé auto-incrémentée

-- MySQL
CREATE TABLE article (
  id INT NOT NULL AUTO_INCREMENT,
  ...
  PRIMARY KEY (id)
);
-- SQLite
CREATE TABLE article (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  ...
);
  • SQLite condense tout en une seule colonne : INTEGER PRIMARY KEY AUTOINCREMENT
  • AUTOINCREMENT est même optionnel dans la plupart des cas : id INTEGER PRIMARY KEY suffit déjà à obtenir un identifiant auto-incrémenté (basé sur le rowid interne), AUTOINCREMENT garantit juste que les id supprimés ne sont jamais réutilisés

Clé étrangère

-- MySQL
CREATE TABLE article (
  ...
  type_article_id INT,
  FOREIGN KEY (type_article_id) REFERENCES type_article (id)
);
-- SQLite
CREATE TABLE article (
  ...
  type_article_id INTEGER,
  FOREIGN KEY (type_article_id) REFERENCES type_article (id)
);

  • Syntaxe de déclaration quasi identique

  • Différence importante : en SQLite, les clés étrangères existent dans le schéma mais ne sont pas vérifiées par défaut. Il faut activer leur contrôle à chaque connexion :

    PRAGMA foreign_keys = ON;

    (sinon on peut insérer une valeur qui ne correspond à aucune ligne de la table référencée, sans erreur)

Ambiguïté des colonnes (GROUP BY / ORDER BY)

MySQL tolère les noms de colonnes non qualifiés même en cas d’ambiguïté entre tables jointes. SQLite est plus strict :

-- fonctionne en MySQL, échoue en SQLite : ambiguous column name: id
SELECT type_article.libelle, type_article.id, count(article.id) as nbr_articles
FROM type_article
LEFT JOIN article ON type_article.id = article.type_article_id
GROUP BY libelle, id
ORDER BY libelle;
-- correction : qualifier les colonnes
GROUP BY type_article.libelle, type_article.id
ORDER BY type_article.libelle;

pymysql (MySQL) sqlite3

ALTER TABLE

  • MySQL : très permissif — ajouter/supprimer une colonne, changer un type, renommer, etc.
  • SQLite : historiquement très limité — on ne peut qu’ajouter une colonne (ALTER TABLE t ADD COLUMN ...) ou renommer une table/colonne. Pour modifier un type ou supprimer une colonne, il faut recréer la table et recopier les données.

Fonctions et syntaxes spécifiques

Besoin MySQL SQLite
Date/heure courante NOW(), CURDATE() datetime('now'), date('now')
Concaténation CONCAT(a, b) a \|\| b
Limiter les résultats avec décalage LIMIT offset, count (ou LIMIT count OFFSET offset) LIMIT count OFFSET offset uniquement

Concurrence et administration

  • MySQL : moteur client-serveur, gère nativement plusieurs connexions simultanées ; nécessite un serveur à administrer (utilisateurs, droits, réplication…)
  • SQLite : un simple fichier .db, pas de serveur, pas de notion d’utilisateurs/droits au niveau de la base ; verrouillage global en écriture (convient à un projet pédagogique ou une petite appli, pas à une forte charge concurrente)
